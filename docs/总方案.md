## 结论

新建一个单进程、单管理员的 iCloud Hide My Email 接码服务。管理员登录 Apple、保存账号、创建和删除隐私邮箱。外部程序只走接码接口领取邮箱和读取验证码，不能进入管理页，也不能用管理员 Cookie 代替接口密钥。

数据库只用 PostgreSQL。界面和错误文案用简体中文。发布身份是 `biubiubiu125`。仓库地址是 `https://github.com/biubiubiu125/icloud-mail`。模块路径是 `github.com/biubiubiu125/icloud-mail`。镜像名是 `ghcr.io/biubiubiu125/icloud-mail`。每次 push 到该仓库，以及手动触发工作流，都会自动构建并推送这个镜像。

协议客户端从本机旧项目复制后改包名。租约、包拆分、后台取信节奏和 Message-ID 去重方向只借鉴 v2 的思路，没有复制 v2 源码。v2 没有许可证。

## 为什么要新建

旧项目已经能登录、创建隐私邮箱、IMAP 取信和按密钥取验证码。它的持久化是整份 `data/state.json`。领取、删除确认和导出回滚都压在同一个文件上，不适合继续加功能。

公开的 v2 包结构更清楚，也有租约，但它没有账号代理、远端删除状态机、导出失败回滚和创建结果待核对。这些是事故防线，不是多余代码。把 v2 拉下来再把旧行为补回去，等于重写，而且不能复制它的源码。

所以协议从旧项目带走，存储、接码、删除状态机和管理页重新写。多用户去掉。远端删除保留。

## 使用角色

管理员只有一个。管理员可以创建账号、保存代理、登录 iCloud Web 或 Apple Account、保存 IMAP、同步远端邮箱、创建隐私邮箱、远端删除、导出接口地址、改设置和看事件。

外部调用方没有管理账号。它用全局接口密钥领取邮箱，用每个邮箱自己的密钥读取验证码。领取后的租约可以确认、释放或续期。外部调用方不能改代理、不能登录 Apple、不能删除远端邮箱。

## 必须守住的产品规则

- 只能运行一个进程。账号锁在进程内存里。开两个进程时，锁失效，可能同时创建或删除同一个账号下的邮箱。
- 账号行上的代理是唯一出口。空代理表示直连。登录请求不接受代理字段。
- 两个都写了且不同的账号 ID 不能合并。空账号 ID 的历史会话可以并入当前账号。
- 删除隐私邮箱默认先删远端，再删本地。只清本地记录必须显式确认。未知来源不能访问 Apple。空来源按 `ICLOUD_WEB`。没有匿名 ID 不能调用 Apple。
- 远端删除调用前先写 `pending`。进程在确认结果前退出，启动时把 `pending` 改成 `unknown`。不能把未确认结果当成成功或普通失败。
- 邮箱池为空时返回 HTTP 200 和 `no_available_mailbox`。不要改成 409。现有调用方把 200 加这个错误码当成正常空池。
- 查询邮箱不返回邮箱密钥。领取接口才返回 `api_token` 和 `api_url`。
- 验证码优先走 IMAP。`000000` 永远不是验证码。邮件正文、验证码、Apple 密码和带密钥的 URL 不写日志。
- 导出必须显式选择。响应写失败要恢复原来的导出时间，不能留下 HTTP 200 空文件和已导出标记。

## 逐条功能链路

每一条都写清借鉴了谁的哪一段、新项目落在哪个文件、和来源差在哪里、现在算不算完成。

### 1. iCloud Web 登录

借鉴旧项目 `internal/app/icloud_client.go` 的 Web 登录，以及旧路由 `POST /api/icloud/protocol-login/start`、`POST /api/icloud/protocol-login/2fa`。新入口是 `POST /api/accounts/{id}/login/web/start` 和 `finish`，实现在 `internal/mailbox/login.go`，实际请求仍进协议客户端。

差在哪里：新项目不从请求体读代理。管理 JSON 拒绝未知字段，多传代理字段会被拒绝，不是忽略。服务层只用账号上保存的代理。请求里的新密码和 Apple ID 只在登录态成功写入时一起保存，不写日志。需要二次验证，或登录态写入失败时，不改账号行，也不清空已有会话。管理员单独修改 Apple ID 仍会清空旧会话。登录成功且 Apple ID 相对当前值有实质变化时，合并前丢掉旧会话，只保留这次登录写入的种类；只改大小写或空格不算变化。只改 Apple ID、不改密码时，不把密码清空。

完成：`StartWebLogin` 和 `FinishWebLogin` 在读账号、调用登录客户端、写回会话期间持有现有 `lockAccount`。锁内不会把数据库事务跨过 Apple 调用。写回仍是短事务，在供应商调用返回后才开始。

### 2. Apple Account 登录

借鉴旧项目 `internal/app/apple_auth_client.go` 和 `apple_srp.go`，以及旧路由 `POST /api/apple-account/login/start`、`POST /api/apple-account/login/2fa`。新入口是 `POST /api/accounts/{id}/login/apple/start` 和 `finish`。

差在哪里：和 Web 登录一样，代理只来自账号行。v2 也有 `POST /api/apple-accounts/login/start` 和 `2fa`，但新项目没有借 v2 的登录实现，因为 v2 没有账号代理。

完成：`StartAppleLogin` 和 `FinishAppleLogin` 也持有同一把 `lockAccount`。不另做第二套锁。

### 3. IMAP 登录和取信

借鉴旧项目 `internal/app/imap_client.go` 的 `CheckICloudIMAPLoginWithProxy` 和 `SyncICloudIMAPMessages`，以及旧路由 `POST /api/icloud/imap-login/save`。新入口是 `POST /api/accounts/{id}/imap`。取信由 `internal/mailbox/provider.go` 的 `SyncIMAP` 调用协议函数。

差在哪里：检查 IMAP 时使用账号代理。没有 IMAP 登录态时，不拿 Web 会话冒充 IMAP。

完成：`SaveIMAP` 在读会话、检查 IMAP、写回登录态期间持有同一把 `lockAccount`。IMAP 解析仍把远端 ID 写成 `imap:<uid>`，同时把 `Message-ID` 头放进 `ICloudSyncedMessage.MessageID`。跨通道去重见第 11 条。

取信窗口在 `internal/protocol/imap_client.go` 的 `planIMAPFetch`。搜索起点只看邮箱 `last_sync_uid`。会话里残留的 `imap_last_sync_uid` 不参与搜索，也不能把起点改到它之后。邮箱游标为空时仍按最近 24 小时 `SINCE` 搜索。游标带 `uv:<UIDVALIDITY>:<uid>`。旧的纯数字游标第一次见到 UIDVALIDITY，或已记录的 UIDVALIDITY 变了，都从 `UID 1:*` 重扫，不能拿旧编号继续往后搜。重扫后的空结果只在 UIDVALIDITY 变化时写成新游标，同一 UIDVALIDITY 的空搜索不改原游标。一次同步先按 UID 从旧到新取连续窗口，服务层上限 50。窗口里的每封都取回完整正文后，末尾 UID 才是下次游标；过滤掉的完整邮件仍要前进。正文缺失、正文仍被 200KB 截断，或中间 UID 没有返回时，游标停在缺口之前，不能跳过。被截断的正文按 200KB 继续补齐，直到完整或达到 1MB。搜索结果比窗口长时，额外再取最新的 50 封给当前别名解析验证码，但这部分不能当成游标，避免跳过中间邮件。空搜索不改原游标。`SyncIMAP` 把协议 `LastUID` 交给 `storeSynced`，IMAP 通道不拿单封邮件的 UID 覆盖它。没有真实 IMAP 收件箱验证。

IMAP 分组在 `iCloudIMAPMessagesByMailbox`。已经按 UID 选出的邮件不能再按 `last_sync_at` 提前 2 分钟丢掉。邮件 `Date` 比上次同步早几分钟，只要 UID 还在搜索范围内，就要入库。没有 `Date` 的邮件同样保留，不写成同步时间。空搜索仍会更新 `last_sync_at`，但不能因此丢掉下一封 UID 更新的邮件。这 2 分钟重叠只留给 Web 同步的 `mailboxSyncAfter`；服务层 Web 同步不传 `LastSyncAt`，且 Web 兜底默认关闭。服务层 IMAP 同步传入的 `after` 是空时间，不能用上次同步时间代替它。

### 4. 创建隐私邮箱

借鉴旧项目两条供应商链路，不是借 v2 的创建实现。

- iCloud Web：协议客户端里的 generate、reserve。旧路由是 `POST /api/icloud/mailboxes/create`。
- Apple Account：`CreatePrivacyMailboxWithAppleAccount`。供应商路径包括 `POST /account/manage/email/private/add`，创建后按返回的匿名 ID 再取完整邮箱。

新入口是 `POST /api/mailboxes`。`internal/mailbox/provider.go` 的 `Create` 按通道调用上面两个协议方法。留空时，已有 Apple Account 登录态就用它，否则用 iCloud Web。显式 `apple_account` 或 `icloud_web` 按指定通道。创建调用限制 2 分钟。创建期间持有进程内账号锁，但不在数据库事务里调用 Apple。

不确定结果包括取消、超时、EOF、协议层已有的临时网络错误，以及错误码 `apple_account_create_uncertain`、`icloud_create_uncertain`、`apple_account_create_empty`。出现这些结果，或返回空匿名 ID、空邮箱时，标记账号待核对并停止继续创建。远端已经创建成功后，生成本地密钥或记录 ID 失败，也走同一条停止创建。

本地插入失败时，先确认这个匿名 ID 是否已经属于本地邮箱。已经属于本地行，或这次查询失败时，不删除远端。查询失败还要停止继续创建。只有确认是尚未跟踪的新匿名 ID，才用不受请求取消影响的 30 秒上下文尝试删除刚创建的远端邮箱。回滚失败则标记待核对，错误码 `mailbox_create_persist_and_cleanup_failed`。远端已创建但登录态写库失败时，先标记待核对，再返回 `icloud_session_persist_after_mailbox_create`。`stopCreate` 写待核对标记时也用不受请求取消影响的 30 秒上下文，不能因为调用方已经断开就写不进标记。待核对标记本身写不进去时，返回 `mailbox_create_reconciliation_persist_failed`，并在本进程记住该账号已停止创建，同时把账号、来源、目标和原因写入本地停止文件。环境变量 `ICLOUD_MAIL_HALT_FILE` 指定路径，未设置时使用临时目录 `icloud-mail-create-halt.json`。写入时先写临时文件，再直接改名覆盖，不能先删掉原文件。Windows 不能覆盖改名时才先删除再改名。进程启动时先读这个文件，再尝试把待核对标记写入数据库；写成功就清掉内存和文件里的停止，写失败则两边都保留，调度器和管理端创建都不再调用 Apple。管理员确认清除待核对后，即使库里的标记已经是 false，也要释放内存和文件里的停止。容器部署必须把这个文件放在持久卷上，否则重建容器后停止记录仍会丢失。数据库和停止文件同时不可用时，无法再记住这条停止。

完成：标记待核对时同时写入 `reconciliation_anonymous_id` 和 `reconciliation_email`。两个标识都空时，写入 `unresolved:` 加随机值，避免下一次成功列表把它当成旧数据清掉。`reconcileLocked` 和账号同步都走 `clearReconciliationIfSeen`。待核对来源的列表里没有对应匿名 ID 或邮箱时，保留待核对状态，返回 409 `mailbox_create_reconciliation_required`。只有目标出现，或没有可核对的目标标识且列表本身成功，才清除。旧行没有目标标识时，列表成功仍可清除。这是旧数据的边界。新创建不会再写出这种空目标。管理员确认远端没有遗留后，可以调用 `POST /api/accounts/{id}/reconciliation/clear` 清除。创建返回未知非空来源时，不改写成 `ICLOUD_WEB`，也不调用 Apple 列表或删除。

### 5. 同步远端邮箱列表

借鉴旧项目同步远端 Hide My Email 列表的行为。旧路由是 `POST /api/icloud/mailboxes/sync`。协议方法是 `ListPrivacyMailboxesForOriginWithSessionAndAPIKey`。新入口是 `POST /api/accounts/{id}/sync`。

差在哪里：同来源或空来源的本地邮箱如果远端没有，只写 `remote_missing_at` 并标记不活跃，不自动删除。新导入邮箱生成随机接口密钥，状态为可领取。v2 也有 `POST /api/apple-accounts/{id}/mailboxes/sync`，但新项目没有借它的同步实现。

待核对期间，账号同步只列待核对来源。来源为空时按 `ICLOUD_WEB`。来源非空但未知时返回 409，不访问 Apple。列表成功也不会无条件清除标记，规则和 `reconcileLocked` 相同。

### 6. 远端删除状态机

借鉴旧项目 `internal/app/server.go` 的删除状态机，不是借 v2 的 `remote-clean`。

旧项目已经有这些错误码和文案：

- `remote_delete_in_progress`：该邮箱已有远端删除操作进行中，请稍后重试。
- `remote_delete_unknown`：上次远端删除在进程退出前未确认结果，请先核对 iCloud 远端状态后再重试。
- `remote_delete_failed`：上次远端删除失败，请先重试远端删除，或确认已核对 iCloud 后再清理本地记录。

旧删除入口是 `DELETE /api/mailboxes/{id}`。供应商动作是先 `POST /v1/hme/deactivate`，再 `POST /v1/hme/delete`。Apple Account 通道走协议客户端里的对应删除方法。

新入口是 `POST /api/mailboxes/{id}/delete` 和 `DELETE /api/mailboxes/{id}`。判断在 `internal/mailbox/delete.go` 的 `planDelete`。供应商调用在 `internal/mailbox/provider.go` 的 `Delete`：`APPLE_ACCOUNT` 调 `DeletePrivacyMailboxWithAppleAccount`，`ICLOUD_WEB` 调 `DeletePrivacyMailbox`，其他来源直接拒绝。

新项目在旧状态机上补了一条：删除状态为空时，只清本地必须带 `confirm_local`，否则 409 `remote_delete_required`，文案是 `删除邮箱必须先删除远端 Hide My Email，不能只清本地记录`。省略 `delete_remote` 表示先删远端再删本地。

调用前把状态写成 `pending`。已经是 `pending` 则拒绝。供应商结果不确定时写成 `unknown`，否则写成 `failed`。先落库，再返回错误。供应商调用返回后的状态写入、事件和本地清理，都用不受请求取消影响的 30 秒上下文。请求在 Apple 调用期间断开时，不能把状态留在 `pending`。启动时 `NormalizeInterruptedDeletes` 仍把进程退出前遗留的 `pending` 改成 `unknown`。成功标记或未知标记写入失败时最多重试 3 次；仍写不进去的 `pending`，后台清理超过 5 分钟后也改成 `unknown`。文案固定为 `上次远端删除在进程退出前未确认结果，请先核对 iCloud 远端状态后再重试`。

未知来源返回 400 `remote_origin_unknown`，文案是 `未知远端来源，已拒绝访问 Apple`。空来源按 `ICLOUD_WEB`。缺少匿名 ID 返回 409 `remote_anonymous_id_missing`，文案是 `缺少远端匿名 ID，已拒绝调用 Apple，本地记录仍保留`。不发明 Apple 的“邮箱不存在”错误码。

远端删除成功后，登录态写库失败只记警告 `session_persist_after_delete`，仍继续删除本地记录。本地删除失败返回 500 `mailbox_delete_persist_failed`，文案是 `远端已删除，但本地记录删除失败，请重试本地清理`。

账号下仍有邮箱时，删除账号返回 409 `account_has_mailboxes`，文案是 `请先逐个远端删除该账号下的邮箱`。这条是新服务的保护，不是从 v2 借的。

### 7. 代理和会话合并

借鉴旧项目的代理权威，不是借 v2。v2 对照副本里没有可用的账号代理链路。

新实现在 `internal/protocol/session_helpers.go` 的 `MergeSavedSession`，以及 `internal/store` 的 `SaveSession`。`SaveSession` 锁定 `proxy_url, session_json`，合并登录态，但更新语句不写 `proxy_url`。读取会话时用账号代理覆盖会话和每个登录态。账号代理为空时清掉会话里的旧代理。

允许的代理协议只有 `http`、`https`、`socks5`、`socks5h`。单独改代理的入口是 `PUT /api/accounts/{id}/proxy`。

会话账号绑定也来自旧项目规则。两个都写了账号 ID、且账号 ID 不同，返回 409 `session_account_mismatch`，文案是 `登录态属于另一个账号，已拒绝合并`。空账号 ID 可以并入当前账号。

### 8. 公开领取和租约

这是混合链路，必须分开看，不能说整段都来自某一个仓库。

空池语义来自旧项目 `handleClaimMailbox`：池子空时 HTTP 200，错误码 `no_available_mailbox`。v2 的 `handlePublicClaimMailbox` 也是这个状态码和错误码。新项目保留 HTTP 200 和这个错误码，文案用 `没有可领取的邮箱`。不要改成 409。

领取机制借鉴 v2，不借鉴旧项目的“直接标成已领取”：

- v2 段：`ClaimMailboxLease` 在事务里按 `project` 加 `request_id` 找回旧租约，否则把一个可用邮箱改成占用，并写入租约。随后有确认、释放、续期和过期。
- 新项目段：`internal/store/lease.go` 的 `Claim`、`CommitLease`、`ReleaseLease`、`RenewLease`、`ExpireHeldLeases`。挑选邮箱用 PostgreSQL `FOR UPDATE SKIP LOCKED`，不是 v2 的进程互斥锁加 SQLite。

差在哪里：

- v2 的占用状态叫 `reserved`，新项目租约状态叫 `held`，邮箱状态改成 `used`。
- v2 请求字段有 `ttl_seconds` 和 `note`。新项目请求字段是 `project`、`purpose`、`request_id`、`account_id`、`ttl_minutes`。默认 30 分钟，最长 10080 分钟。
- v2 有按租约 ID 查询和写备注。新项目没有这两条路由。
- 同一 `project` 加 `request_id` 只有在这笔领取仍独占邮箱时才返回当前密钥，`idempotent` 为 true，`created` 为 false。并发插入冲突返回 409 `request_id_conflict`。邮箱已回到可领取池时，重复请求会重新占用并返回轮换后的密钥。重新占用没带备注时写成 `已领取`，不能把备注清空。租约已经到期、但邮箱仍是 `used` 且 `active_lease_id` 还指向这笔租约时，不延长 `expires_at`，也不返回密钥，直接 409 `request_id_not_reclaimable`。等过期任务把邮箱放回池后，同一请求才能重新占用。邮箱已被别人占用、删除或不可领取时，同样返回这个 409，响应里没有密钥。账号过滤不一致返回 409 `request_id_account_mismatch`，同样没有密钥。
- 领取成功 JSON 有顶层 `id`、`email`、`api_token`、`api_url`，以及嵌套 `mailbox`、`lease`、`created`、`idempotent`。没有额外的 `key` 或 `api_key` 字段。这是为了让旧调用方还能读到邮箱和密钥，不是把 v2 的响应原样搬过来。v2 把邮箱和租约放在 `data` 下面。

新领取会在同一事务写入 `code_not_before` 为领取时间，并删除该时间及之前的邮件。同一笔仍独占的重放不会改这个时间，也不会删掉领取之后的邮件。确认只接受未过期的 `held`，否则 `lease_not_held` 或 `lease_expired`。释放接受 `held` 或 `committed`，否则 `lease_not_releasable`。仍是 `held` 时释放会回到 `available`，并在同一条更新里轮换 `api_token`，同时写入 `code_not_before`，删掉该时间及之前的邮件。已经确认的租约只有 `return_to_pool` 为 true 才回到 `available`、轮换密钥并切断旧验证码，否则只清 `active_lease_id`，原持有者仍可用原密钥取码，历史邮件也不清。续期只接受未过期的 `held`。过期任务每 30 秒把到期的 `held` 标成 `expired`，并把仍由该租约占用的 `used` 邮箱放回 `available`，同时轮换密钥并切断旧验证码。领取和续期请求没带 `ttl_minutes` 时，都使用设置里的 `lease_ttl_minutes`，不是固定 30 分钟。邮箱密钥走的确认、释放和续期，会在同一事务里再核对密钥和当前租约；全局密钥路径不核对邮箱密钥。按邮箱变更租约的入口是 `internal/httpapi/public.go` 的 `handleEmailLease`。公开接口关闭时先返回 403 `public_api_disabled`，不能先返回 404 `lease_not_found`。错误密钥仍是 401 `api_key_invalid`，不先暴露邮箱或租约是否存在。

### 9. 查询邮箱

路由形状同时存在于旧项目 `POST /api/v1/mailboxes/lookup` 和 v2 的同名路由。新项目保留这个路径。一次查询 1 到 500 个邮箱，超出返回 `lookup_size_invalid`。

必须保住的行为是查询结果清空 `api_token`。领取接口才返回密钥。管理员 Cookie 不能代替全局密钥。

### 10. 按邮箱取验证码

路由来自旧项目 `GET /api/v1/mailboxes/{email}/code`，处理函数是 `handleMailboxCodeByEmail`。v2 也有同名路由，但验证码提取规则按旧项目。

旧项目的提取规则落到新项目 `internal/protocol/otp.go` 的 `extractOTP`：6 位数字前后 80 个非数字字符内要有 `openai`、`chatgpt`、`otp`、`code`、`verification`、`验证码`、`验证` 或 `代码`。不再匹配裸 6 位数字，避免把订单号当成验证码。`000000` 永远不是验证码。`验证` 可能匹配得比较宽，这是沿用旧规则，不是新发明。

新项目的等待、缓存和关键词在 `internal/mailbox/code.go`、`messages.go`。查询参数是 `keyword`、`after`、`wait_ms`、`cache=1`、`allow_stale=1`。`after` 必须是 RFC3339，否则 400 `invalid_after`。等待最长 30 秒，轮询间隔 2 秒。默认只接受 5 分钟内的新验证码。新领取和回到可领取池时写入的 `code_not_before` 是下限：这个时间及之前的邮件对任何 `after` 都不可见，5 分钟窗口在没传 `after` 时仍然生效。关键词默认 `OpenAI`，`*` 表示不按关键词过滤。

取码优先 IMAP。没有 IMAP 且 Web 兜底关闭时返回 `imap_session_missing`，不访问 Apple。Web 兜底这个开关的方向借鉴 v2 的 `EnableWebBackgroundMail`，默认关闭。Web 同步先取邮件正文，再按主题加正文判断是不是验证码，不能只凭预览跳过。删除状态为 `pending` 时停止取信。返回验证码前会重新核对邮箱密钥；同步期间密钥已轮换则返回 404，不交出验证码。新鲜缓存可以挡住一次同步错误；过期缓存只有显式 `allow_stale=1` 才能挡住。没有可用缓存时，同步失败返回同步错误，不能收成 404 `code_not_found`。读取邮件失败也返回数据库错误，不能当成还没有验证码。`cache=1` 不触发同步。成功同步没有新邮件时，不把 `last_sync_uid` 写成空。IMAP 有搜索结果时，游标前进到本次连续旧窗口的末尾，不因为过滤后没有保留邮件就停住。已经按 UID 搜索到的邮件不能再按 `last_sync_at` 提前 2 分钟丢掉；`Date` 比上次同步早、但仍在 5 分钟窗口内的验证码必须能入库。没有日期的邮件也要入库，之后仍不能当成新验证码。同一次取码请求不会重读刚写下的 `last_sync_at`，IMAP 也不再拿这个时间做丢信下限。Web 同步不把网页邮件 UID 写进 `last_sync_uid`，避免后来的 IMAP 搜索从错误编号之后开始。Web 同步同时做无过滤搜索和别名搜索，单次最多 50 封；别名搜索被拒绝时仍使用无过滤结果，不发明未证实的分页字段。已经写进库的网页 UID 不会自动清掉。`source` 按实际通道写 `imap`、`web` 或 `cache`，不再把 Web 结果标成 `imap`。重复同步不会把已有邮件的 `received_at` 改晚。没有 `Date` 或解析失败的邮件不写成同步时间，`received_at` 保持空时间，因此不能越过 `code_not_before`，也不能当成 5 分钟内的新验证码。空时间或公元 1 年不能覆盖已有真实收信时间；之后同步到真实时间时可以补上。没有验证码的正文不能覆盖已有验证码正文。保留清理不会删除空时间或公元 1 年的邮件。

公开领取、查询、取码和租约变更都要求公开接口开启。关闭后这些入口都是 403 `public_api_disabled`。按邮箱确认、释放或续期在 `handleEmailLease` 里先判断公开接口，没有活动租约时也不能先返回 404 `lease_not_found`。错误密钥仍是 401 `api_key_invalid`。邮箱密钥放在 `key` 查询参数或 `X-Mailbox-Key`。

完成：邮箱密钥比较在 `internal/domain/rules.go` 的 `TokenMatches`。空密钥不匹配。算法仍是 `subtle.ConstantTimeCompare`，和全局密钥相同，没有改成另一套。取码和邮箱租约鉴权都走这个函数。

### 11. 邮件去重

方向借鉴 v2 的 `canonicalMailID`：同一个 `Message-ID` 不管来自 IMAP 还是 Web，都应该得到同一个去重键。v2 在 IMAP 解析时直接读 `Message-ID` 头。

完成：`parseICloudIMAPMessage` 把 `Message-ID` 头写入 `ICloudSyncedMessage.MessageID`。Web 同步优先从长邮件头读 RFC `Message-ID`，没有这个头时才用 iCloud 的 `messageId`。`canonicalID` 先用这个字段，再从旧正文里的 `Message-ID:` 回退，再用 `remote:<远端 ID>` 和 `uid:<UID>`。规范化会去掉尖括号并转成小写。没有 `@` 的内部 ID 不当成 Message-ID。

差在哪里：去重前缀仍是 `mid:`，不是 v2 的 `message-id:`。没有借 v2 的 `mail-hash:` 回退。已经按 `remote:` 或 `uid:` 落库的旧邮件不会被回写。下一次同步可能再插入一条 `mid:` 记录。这不是实时收信已验证。

### 12. 导出接口地址

行为合同来自旧项目 `GET/POST /api/runtime/export-mailbox-apis`：只导出显式选中的邮箱；响应写失败要恢复原来的 `APIExportedAt`，不能留下 HTTP 200 空文件和已导出标记。

新入口是 `POST /api/mailboxes/export`。必须显式给出邮箱 ID，最多 500 个。空 ID 或不存在的 ID 返回 400 `export_selection_missing`。超过 500 返回 `export_selection_too_large`。导出 JSON 只有 `email`、`api_url`、`api_token`。先标记已导出，再读取并生成完整 JSON。读取失败或响应写失败都调用恢复，把 `api_exported_at` 改回原值。恢复使用 `RestoreContext`：从请求上下文去掉取消，再给 15 秒超时。请求断开不能把恢复一起取消。恢复失败要记日志，不能假装已经回滚。文件名是 `mailbox-apis.json`。

差在哪里：旧项目还有导出纯邮箱地址和取消导出标记。新项目没有这两条。v2 也有 `GET /api/runtime/export-mailbox-apis`，但新项目没有复制它的实现。

未验证：导出响应写到一半断开的 HTTP 客户端没有再测。已有单元测试证明父上下文取消后，恢复上下文仍然可用。库层恢复和先生成 JSON 再写响应已有代码。

### 13. 单管理员登录

方向借鉴 v2 的 `GET /api/auth/status`、`POST /api/auth/setup`、`POST /api/auth/login`、`POST /api/auth/logout`。不借鉴旧项目的多用户注册。

新项目只在管理员表为空，且用户名至少 3 位、密码至少 8 位时创建唯一管理员。已有管理员时，环境变量和初始化接口都不能再覆盖。密码不写日志。Cookie 名是 `icloud_mail_session`，只存 SHA-256。Cookie 是 HttpOnly、SameSite Lax。`Secure` 由配置或 HTTPS 基址决定。

管理写操作还要求请求头 `X-Requested-With: icloud-mail`。同一来源 10 分钟 8 次密码错误后，下一次登录返回 429 `rate_limited`。成功登录和 JSON 解析失败不计数。这是新项目自己的限制，不是从 v2 复制的阈值。创建管理员时锁住管理员表，避免并发初始化写出两个管理员。完成登录前会核对挑战属于当前账号；进程重启后未完成的挑战不能提交到别的账号。

### 14. 设置、事件和后台任务

设置页面的方向借鉴 v2 的 `GET /api/settings`、`PUT /api/settings` 和 `GET /api/events`。字段不是照搬。

新项目设置是 `id = 1` 的单行。公开接口默认开启。关键词默认 `OpenAI`。租约默认 30 分钟，最长 10080 分钟。邮件默认保留 90 天。自动创建默认关闭，间隔 300 秒，每轮 1 个；保存时每轮超过 20 会收到 20，间隔低于 30 秒会抬到 30 秒。后台取信默认开启，间隔 60 秒；保存时低于 15 秒会抬到 15 秒。Web 取码兜底默认关闭。

保存设置时，空的 `api_key` 和 `apple_account_api_key` 保留库里的旧值。其他字段按请求整体覆盖，所以调用方必须提交 GET 得到的完整对象。

后台三个循环都在 `internal/mailbox/background.go`：过期租约和旧邮件、后台取信、可选自动创建。可取消和抖动借鉴 v2 的 `mailwatcher`，没有借 IMAP IDLE。自动创建默认关闭，跳过待核对账号，也跳过本进程已经因为待核对标记写失败而停止创建的账号，备注写 `scheduler`。一轮里某个账号创建失败就停止该账号本轮剩余数量。过期租约、读设置和删旧邮件失败时写日志。后台取信读设置或邮箱列表失败，以及自动创建读设置或账号列表失败时，也写日志。日志不含连接串或密码。循环 panic 只记任务名，不记邮件正文或验证码。

不借 v2 的 ServerChan 测试、更新检查、数据库备份和实时推送。

### 15. 管理页

不借 v2 的 Vue，也不把旧项目的多页模板搬过来。新管理页是 `internal/httpapi/admin.html`，由 `GET /` 内嵌返回，不引用外部 CDN。页面要能完成初始化、登录、账号、代理、两种登录、IMAP、同步、创建、远端删除确认、导出、设置和事件。删除按钮按 `remote_delete_status` 发送 `confirm_unknown`、`confirm_failed` 或 `confirm_local`。`pending` 只显示刷新提示。待核对账号有“我已在 iCloud 核对，清除待核对”按钮。

## 当前启动链路

1. 读取 `-config`，默认 `config.json`。文件不存在不算错误。同名环境变量优先。
2. 连接 PostgreSQL，执行内嵌 `internal/store/schema.sql`。迁移版本是 `1`。重复启动不能重复插入设置行。
3. 把删除状态 `pending` 改成 `unknown`。日志只记数量。
4. 没有管理员且用户名、密码符合长度时，才创建唯一管理员。已有管理员时，环境变量里的短用户名或短密码不阻止启动，也不覆盖已有管理员。
5. 设置表的全局接口密钥为空时，才写入 `ICLOUD_MAIL_API_KEY`。已有密钥不能被空值覆盖。
6. 启动三个后台循环。
7. HTTP 同时提供管理页、管理接口和公开接码接口。

HTTP 超时：请求头 10 秒，读和写各 3 分钟，空闲 60 秒，关闭 10 秒。3 分钟是为了 Apple 登录和创建不被 30 秒切断。

## 数据

只使用 PostgreSQL。表是 `schema_migrations`、`admins`、`admin_sessions`、`settings`、`accounts`、`mailboxes`、`mailbox_leases`、`messages`、`events`。

账号列表 JSON 不返回 `apple_password` 和 `proxy_url`，只返回 `has_password` 和 `has_proxy`。管理员点开某个账号时，`GET /api/accounts/{id}` 才返回这一条的登录邮箱、密码和拆开的代理。接码接口不返回这些字段。会话 JSON 里的代理不是权威值。权威值是 `accounts.proxy_url`。

邮箱地址唯一。领取条件是状态 `available`、`api_active`、`icloud_active`、`active_lease_id` 为空、`remote_delete_status` 为空。可选再按 `account_id` 过滤。

邮件唯一键是 `(mailbox_id, canonical_id)`。正文最多保存 200000 个字符。消息 JSON 不返回正文。

## 已收口

上一版总方案里的四项已经写进当前代码。不要再把它们写成未修改。

1. Web 登录、Apple Account 登录和保存 IMAP 在读会话、调用供应商、写回会话期间持有现有 `lockAccount`。数据库事务不跨过供应商调用。没有第二套锁。
2. 待核对目标写在 `accounts.reconciliation_anonymous_id` 和 `reconciliation_email`。列表里没有对应匿名 ID 或邮箱时不清除，返回 409 `mailbox_create_reconciliation_required`。没有目标标识且列表成功才清除。新创建如果两个标识都空，会写入 `unresolved:` 哨兵，不能再靠空目标自动清除。
3. 邮箱密钥用 `TokenMatches` 做常量时间比较。空密钥不匹配。全局密钥仍用原来的 `subtle.ConstantTimeCompare`。
4. IMAP 解析保存 `Message-ID` 头，`canonicalID` 优先使用它。Web 长邮件头里的 RFC `Message-ID` 也进同一个字段。
5. 管理端 `PATCH /api/mailboxes/{id}` 只改标签、备注和接口开关。请求体必须带 `api_active`。`status` 和 `icloud_active` 会被严格 JSON 拒绝，不能把仍有效的密钥放回可领取池。
6. 新领取、回到可领取池或过期时，同一事务写入 `code_not_before`，并删除该时间及之前的邮件。回池和过期还会轮换密钥。同一笔领取的重放不重置这个时间。确认后不回池的释放不切断领取之后的邮件。
7. 续期没带时长时使用设置里的 `lease_ttl_minutes`。邮箱密钥操作租约时，同一事务再核对密钥和当前租约。
8. 取码在返回前重核密钥。邮件列表错误和没有缓存的同步错误都不再收成 404。
9. 没有配置公开基址时，`api_url` 是相对路径。创建得到未知非空来源时不改写成 `ICLOUD_WEB`，后续同步也不访问 Apple。
10. 删除账号先持有账号锁，再在事务里锁定账号行、清点邮箱并删除。仍有邮箱时返回 409。
11. IMAP 游标按本次连续旧窗口的末尾前进，过滤掉的邮件不能让游标停住。积压时额外读取最新窗口，但游标不跳到最新窗口。
12. 导出恢复不使用已被取消的请求上下文。父上下文取消后，恢复上下文仍可用。
13. 到期后的同一 `request_id` 不再延长租约，也不返回旧密钥。邮箱回到可领取池之前，重复请求是 409。
14. 没有可解析日期的邮件不写成同步时间，不能越过领取或回池时写入的 `code_not_before`。
15. 创建待核对标记使用不受请求取消影响的 30 秒上下文。标记写不进去时，本进程停止该账号继续创建，调度器和管理端重试都不再调用 Apple。
16. 远端删除返回后的状态写入不使用已取消的请求上下文。取消或超时不再把邮箱留在 `pending`。
17. Web 同步不推进 `last_sync_uid`。网页 UID 不能变成后续 IMAP 搜索的起点。
18. 远端已创建但本地密钥或记录 ID 生成失败时，先标记待核对，再返回原因错误。标记失败则返回 `mailbox_create_reconciliation_persist_failed`。
19. 过期任务的数据库错误会写日志。日志不包含连接串或密码。
20. 已有管理员时，过短的启动账号或密码不阻止进程启动。
21. IMAP 不再用上次同步时间提前 2 分钟丢掉已按 UID 选出的邮件。没有日期的邮件同样保留，不写成同步时间。
22. 公开接口关闭时，按邮箱变更租约先返回 403 `public_api_disabled`，再判断有没有活动租约。错误密钥仍是 401。

这些之外仍然不加 Vue、ServerChan、自动更新、多用户或代理池。

## 风险和回滚

新项目是独立目录和新库。回滚就是停止新进程，不使用新库。不要把新表迁回旧项目的 `state.json`。旧项目可以继续按原来的方式运行。

如果新库里已经有领取记录或 Apple 会话，停止前先导出数据库。删除本机测试库 `icloud_mail_test` 不影响旧项目，但不要删除用户另外指定的生产库。

单进程是硬约束。空邮箱池保持 HTTP 200。生产环境不要设置 `IPM_DEBUG_APPLE_ACCOUNT`。
